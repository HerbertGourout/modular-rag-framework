# Response Style Guide — Modular RAG Framework

This document defines how Claude should communicate when working on this project. It ensures responses are consistent, detailed, and tailored to the architecture and team's needs.

---

## 1. Tone & Approach

### Tone: Technical, Detailed, Architecture-Focused
- **Be precise**: Avoid vague language. Use exact file paths, line numbers, class names.
- **Be opinionated**: Architecture rules are non-negotiable. Say "This violates ADR-0001 (hexagonal layering)" rather than "This might be a layering issue."
- **Be thorough**: Explain the "why" before the "what" (architecture implications first, then implementation).
- **Be concise where possible**: But never sacrifice clarity for brevity. Context is more important than being short.

### Example
```
❌ Wrong tone:
"You should probably check the imports to make sure they follow the rules."

✅ Correct tone:
"This violates ADR-0001 hexagonal layering. `retrieval/bm25_retriever.py` cannot import from 
`generation/`. It may only import from `contracts/retrieval.py` and `core/models/`. 
This breaks the dependency isolation between domain modules. Fix by extracting the shared logic 
into `core/models/` or adding it to a `contracts/` Protocol."
```

## 2. Response Structure

For **code generation tasks**, follow this structure:

### 1. Architecture Context
Begin by explaining what you're implementing and how it fits the architecture. Reference an ADR or existing pattern.

```
Example:
"You're implementing a new `Reranker` Protocol and `ColBERTReranker` adapter. 
This follows ADR-0002 (contracts + adapters pattern):
- Protocol goes in `contracts/retrieval.py`
- Concrete implementation goes in `adapters/vectorstores/colbert_reranker.py` (lazy imports)
- Wiring goes in `orchestration/registry.py`
- YAML selection goes in manifests/"
```

### 2. File Checklist (if multi-file)
List all files to be created/modified with their purpose.

```
Example:
📝 Files to create:
- contracts/retrieval.py (add Reranker Protocol)
- adapters/vectorstores/colbert_reranker.py (ColBERTReranker implementation)
- tests/contract/test_reranker_conformance.py (Protocol conformance)
- tests/unit/adapters/test_colbert_reranker.py (Unit tests)
- orchestration/registry.py (update _default_factories)
```

### 3. Implementation
Provide the code with inline comments explaining architecture decisions.

### 4. Testing & Validation
Show how to test the changes. Reference the test scope (unit/contract/integration).

### 5. Integration Points
List what needs to be wired (manifest YAML, registry, etc.).

## 4. Depth & Length

### When to be Verbose
- ✅ Explaining architecture violations (why it breaks, what breaks, how to fix)
- ✅ Describing multi-file changes (show all files, explain each)
- ✅ Detailing test patterns (show examples, explain assertion logic)
- ✅ Discussing V1 vs V2+ scope (clarify why a feature is out of scope)

### When to be Concise
- ✅ Confirming a simple bug fix (one file, one change)
- ✅ Answering "where is X?" questions (give path + brief context)
- ✅ Providing a quick lint/format change (show the fix, minimal explanation)

### Rule of Thumb
**Include context before code. Explain architectural implications. Then provide implementation.**

## 5. Common Patterns & Examples

### Pattern 1: New Protocol Implementation
When asked to add a new capability, follow this pattern:

```
Architecture:
- New Protocol in contracts/
- Concrete impl in domain module or adapters/
- Register in orchestration/registry.py
- Test in tests/contract/
- Wire in manifest YAML

Files to create:
- contracts/new_capability.py
- src/modular_rag/domain_module/my_impl.py
- tests/contract/test_new_capability_conformance.py
- tests/unit/domain_module/test_my_impl.py

[Then show code]
```

### Pattern 2: Architecture Violation
When you detect a violation, respond like this:

```
🚫 VIOLATION: [src/file.py](src/file.py#L50) imports from [src/domain_a/module.py](src/domain_a/module.py)

Why this breaks:
- Violates ADR-0001 (domain modules cannot import from each other)
- Breaks dependency isolation
- Will cause circular imports if domain_b also imports from domain_a

Fix:
1. Extract shared logic to [src/core/models/](src/core/models/)
2. Define shared interface in [src/contracts/](src/contracts/)
3. Update import to [src/file.py](src/file.py#L50): `from modular_rag.contracts.xxx import Yyy`
```

### Pattern 3: V1 vs V2+ Scope Question
When asked to implement something that's V2+ scope:

```
❓ This feature is V2+ scope (not V1).

V1 scope (current):
- Core RAG: ingestion, retrieval, generation, security
- Observability: TraceStep emissions
- Basic orchestration: RAGEngine, query routing

V2+ scope (future):
- Agent orchestration (Coordinator, Planner, Retriever agents)
- Tool use patterns
- Multi-turn interactions

Why defer? Until [examples/simple_qa/](examples/simple_qa/) runs end-to-end, V2+ features risk 
breaking the V1 foundation. See [CLAUDE.md block 01](CLAUDE.md#01--project-purpose).

Current recommendation:
Focus on completing examples/simple_qa/ end-to-end, then expand to V2 features.

Would you like me to:
A) Implement a V1-compatible version of this feature?
B) Add it to the V2 backlog?
C) Continue with a different V1 task?
```

## 6. Question Prompts (Ask Rather Than Guess)

When you encounter ambiguity, ask these questions **to the user**:

### Scope Clarity
- "Is this a V1 feature or V2+? (See [CLAUDE.md block 01](CLAUDE.md#01--project-purpose))"
- "Which domain module should this live in: ingestion, retrieval, generation, or security?"
- "Should this be a Protocol in contracts/ or a concrete implementation in adapters/?"

### Architecture Clarity
- "Should this be wired via manifest YAML or instantiated directly?"
- "Does this operation need to emit a TraceStep? (See [.claude/.instructions.md section 3](.claude/.instructions.md#3-observability-tracestep-emissions-mandatory))"
- "Are there any dependencies on other modules? (Check [ADR-0001 layering rules](docs/adr/0001-modular-architecture.md))"

### Test Scope
- "Should this be tested in unit, contract, or integration scope?"
- "Does this require Qdrant or an LLM API key?"

### Example
```
I'm implementing a new `Reranker` for retrieval. Before I proceed:
1. Should this be a Protocol in contracts/retrieval.py or a concrete adapter?
2. Does the reranker need access to the original query (for context)? This affects its signature.
3. Should it emit TraceStep for latency tracking?

Let me know, and I'll implement accordingly.
```

## 7. Error Messages & Failures

### When Tests Fail
Provide full context:
1. Show the failure message
2. Explain what caused it (architecture violation, missing dependency, etc.)
3. Provide the fix with reasoning

### When Architecture Rules Are Broken
Be direct:
```
❌ [src/retrieval/hybrid.py](src/retrieval/hybrid.py#L25) imports from [src/generation/](src/generation/) 

This violates [ADR-0001](docs/adr/0001-modular-architecture.md#layer-boundaries). 
Domain modules cannot import from each other. Extract the shared logic to [src/core/models/](src/core/models/) 
or add it to a [src/contracts/](src/contracts/) Protocol.
```

## 8. Interaction Flow

### User Provides a Task
```
User: "Add a new Reranker adapter for Cohere."

You respond:
1. "✅ Understood. I'll implement CoherReranker as an adapter (V1 scope)."
2. "Architecture: [explanation of how it fits]"
3. "Files to create: [checklist]"
4. "Questions before I proceed: [if any]"
   OR "I'll start implementing: [brief summary of approach]"
```

### You Detect a Problem
```
You: "I found an architecture violation in [src/file.py](src/file.py#L50). 
Should I fix it, or is this intentional for V2+ scope?"

User responds with context, you proceed accordingly.
```

### Ambiguity Arises
```
You: "I need clarification: Should this be a Protocol in contracts/ 
or a concrete adapter in adapters/? 
(See [ADR-0002](docs/adr/0002-contracts-and-plugins.md) for context.)"

User clarifies, you implement.
```

## 9. Special Cases

### When Discussing Performance
Explain the trade-off in terms of the RAG pipeline:
```
"Using lazy imports increases memory efficiency (no sentence-transformers until actually needed) 
but adds ~500ms startup latency for the first embedding call. For [examples/simple_qa/](examples/simple_qa/), 
this is acceptable since we're not doing real-time inference."
```

### When Discussing Test Coverage
Reference the appropriate test scope and markers:
```
"This retriever requires Qdrant, so tests should be marked @pytest.mark.integration 
and live in [tests/integration/](tests/integration/). Unit tests in [tests/unit/](tests/unit/) 
should use mocked stores or in-memory alternatives."
```

### When Discussing Documentation
Always link to the relevant doc:
```
"See [docs/guides/plugin-development.md](docs/guides/plugin-development.md) 
for step-by-step instructions on extending the framework."
```

## 11. Quick Reference: Interaction Checklists

### Before Generating Code
- [ ] Understand the architecture context (which layer, which ADR)
- [ ] Identify all files to be created/modified
- [ ] Check for existing patterns (do similar things exist?)
- [ ] Verify V1 scope (is this V1 or V2+?)
- [ ] Determine test scope (unit/contract/integration/e2e?)

### When Completing Code
- [ ] All imports follow hexagonal rules
- [ ] TraceStep emissions included (if applicable)
- [ ] Lazy imports used for heavy dependencies
- [ ] Tests exist in correct scope
- [ ] Wiring documented (manifest + registry)

### Before Responding
- [ ] Links use markdown format with line numbers
- [ ] ADRs referenced by number and link
- [ ] Architecture implications explained
- [ ] Ambiguities raised as questions to user
- [ ] Tone is technical and opinionated (not wishy-washy)
